## Context

The companion change defines ports, deterministic deck services, SQLite, Wails,
policy-controlled tools, and audit events, but it does not define an executable
workflow model. The architecture now also distinguishes a product frontend, local
backend, central backend, and a development-only MCP. Workflows must run offline,
remain inspectable after interruption, and be testable without MTGA, a network, or
an LLM. The existing Python application remains unchanged during this change.

## Goals / Non-Goals

**Goals:**

- Make every multi-step application activity a typed, versioned, bounded graph.
- Execute identical graph and application code in production and in the harness.
- Persist enough state and redacted evidence for recovery and deterministic tests.
- Isolate effects, approvals, development tooling, and external dependencies.
- Support local SQLite now and a storage port suitable for central jobs later.

**Non-Goals:**

- Representing every domain function, SQL query, or UI interaction as a graph.
- Accepting executable graph definitions generated by a model or remote catalog.
- Providing arbitrary SQL, shell, filesystem, or production access through MCP.
- Implementing distributed consensus, full event sourcing, or a Temporal cluster.
- Replacing the legacy Python application as part of this change.

## Decisions

### 1. Define an activity by orchestration responsibility

An activity is an externally initiated or scheduled use case with multiple steps,
a side effect, a retry boundary, an approval, or resumable state. Each activity
MUST register one compiled Go `GraphDefinition` containing kind, version, initial
node, nodes, transitions, terminal outcomes, limits, and recovery policy. Pure
normalization, matching, legality, and ranking remain deterministic node services.

Initial graph kinds are `collection-sync`, `meta-deck-recommendation`,
`approved-export`, `telemetry-flush`, and `development-scenario`. A model may
select registered tools or return typed node output; it cannot add transitions.

### 2. Build a small explicit engine around ports

Use `internal/workflow` for definitions, engine, limits, and typed errors, with
activity graphs under `internal/workflows/<kind>`. The engine calls `Node.Execute`
and resolves the next node from the registered transition table. A composition
root injects clock, ID source, run store, policy, approval store, tool registry,
effect executor, and event sink. No external workflow engine is needed initially.

This keeps local execution offline and dependency-light. Reconsider a distributed
orchestrator only if measured central workflows require cross-service scheduling.

### 3. Checkpoint state; do not use full event sourcing

SQLite stores graph definitions by identity, run state, step attempts, approvals,
effect idempotency keys, and an outbox. Each node result and next state commit in
one transaction using an optimistic run version. Events are an audit journal; the
checkpoint and domain snapshots remain authoritative. A run pins its graph version.

Effects execute only through typed adapters. The outbox provides at-least-once
delivery, so every effect MUST have an idempotency key. Recovery acquires a bounded
lease and resumes only from the last committed node; incompatible versions fail.

### 4. Apply hard execution and policy limits

Initial defaults are eight steps, six tool calls, two identical tool-and-argument
calls, and a 30-second active deadline. Graph definitions may lower these values
but cannot exceed centrally configured hard caps. Waiting for approval is persisted
and does not consume active time. Cancellation and deadline signals reach every node.

### 5. Make the harness a production composition profile

`internal/testkit` builds the production engine with a temporary database, sanitized
fixtures, controlled clock and IDs, scripted planner, fake boundary adapters, and
fault decorators. Scenarios are Go values with an optional versioned JSON form.
The harness invokes the public activity entry point and asserts state, events,
effects, limits, persistence, and redaction. It never reimplements transitions.

Profiles are deterministic, integration, end-to-end, staging, and optional provider
smoke. Only staging may use network resources, and it requires an explicit allowlist.

### 6. Keep workflow evidence private and bounded

Every event carries schema version, run and step IDs, graph identity, correlation
and causation IDs, timestamp, outcome code, duration, and redacted attributes.
Inputs, collections, logs, paths, credentials, model prompts, and tool payloads are
not event fields. Replay is a dry-run against captured fixture references and hashes;
it never repeats an external effect automatically.

### 7. Expose constrained development MCP tools

`cmd/dev-mcp` exposes graph listing, scenario execution, run inspection, event
validation, and fixture diagnostics over stdio. It has no generic database or shell
tool. Startup rejects production DSNs and hosts; read access is the default, while
scenario execution requires an explicit development capability. It is omitted from
desktop and central production packaging.

### 8. Enforce small source files without fragmenting ownership

CI limits manually maintained Go files to 100 physical lines. Generated bindings,
lockfiles, migrations, and fixture data are excluded. Each file owns one concept,
while packages retain cohesive APIs; formatting tricks do not satisfy the gate.

## Risks / Trade-offs

- **Graphs add ceremony to simple work** -> Apply the activity definition and keep
  pure calculations as functions inside nodes.
- **At-least-once effects can duplicate actions** -> Require persistent idempotency
  keys and test crash points before and after effect acknowledgement.
- **Recorded evidence can leak collection data** -> Use an allowlisted event schema,
  payload hashes, automated forbidden-field tests, and bounded retention.
- **A 100-line gate can create excessive files** -> Review package cohesion and allow
  documented, time-bounded exceptions only when splitting would hide ownership.
- **Two active changes can conflict** -> Implement after companion domain and port
  contracts exist; revise its product-MCP tasks before enabling development MCP.

## Migration Plan

1. Correct the companion change so MCP is legacy or development-only.
2. Add graph contracts, registry validation, in-memory store, and deterministic tests.
3. Add SQLite migrations and crash-safe checkpoint, lease, outbox, and recovery tests.
4. Move one vertical slice, `meta-deck-recommendation`, behind the graph entry point.
5. Add remaining local graphs, typed frontend progress, and the scenario harness.
6. Add observability, retention, development MCP, CI gates, and staging tests.
7. Roll back per activity by selecting its previous entry point while preserving runs.
